The Problem

Robot motor control is stuck in the 1990s

Every production robot today ships with a hand-coded control stack. Separate C++ modules for walking, turning, balancing, recovering from falls — each one painstakingly tuned by control engineers over months. A typical quadruped carries 50,000–100,000 lines of C++ just to walk and not fall over.

Adding a new behavior — stair climbing, rough terrain, carrying a payload — means months of engineering. Each new behavior can break existing ones. Each new robot morphology means starting over.

Model Predictive Control (MPC) improved things, but it solves a fresh optimization problem every control cycle. That's O(N³) per timestep. On a humanoid with 40+ degrees of freedom, MPC barely runs at 30–50Hz. Real-time? Barely. Certifiable? Never.

Recent RL-trained neural policies look promising in demos but ship as black boxes with no safety guarantees, no timing determinism, and no path to certification. Every new robot still needs its own policy trained from scratch.

The robotics industry doesn't have a hardware problem. It has a motor software problem. SOMA solves it.

What We're Building

A spinal cord for any robot

Your brain doesn't compute individual muscle torques when you walk. Your spinal cord handles that — taking high-level intent ("walk forward") and converting it into coordinated motor signals, automatically adjusting for terrain, perturbation, and balance. Thousands of capabilities, one system, no conscious computation required.

SOMA is that layer for robots. A high-level planner — any planner — sends a target command. SOMA converts it into safe, coordinated motor torques in a single constant-time forward pass. No iterative solving. No scenario-dependent computation. No separate modules per behavior.

The core architecture is a Closed-form Continuous-time (CfC) neural network — a recurrent network with continuous-time dynamics governed by learnable time constants. Unlike standard neural networks that operate in discrete timesteps, CfC networks have an explicit dt parameter that makes the same trained weights produce correct behavior at any control frequency: 200Hz, 1kHz, 10kHz — with zero retraining.

This isn't a theoretical property. It's a mathematical consequence of the architecture: σ = sigmoid(τ_a · dt + τ_b). The time constants τ_a and τ_b encode the dynamics. Change dt, and the network automatically adjusts its integration. No other neural architecture used in robotics can do this.

Why This Is Hard to Copy

Three architectural moats

Constant-time inference. The CfC forward pass is 178,000 multiply-accumulate operations. Fixed. Every cycle. Standing still or mid-backflip — same compute, same latency. MPC's cost scales with planning horizon and contact complexity. Standard MLPs don't have continuous-time dynamics. You can't retrofit this property onto an existing architecture; it has to be designed in from the beginning.

Frequency invariance. Train once, deploy at any control rate. The CfC's time constants (τ_a, τ_b) encode how fast the hidden state should evolve relative to real time. At 200Hz, dt=0.005. At 10kHz, dt=0.0001. The network compensates automatically. A standard MLP policy trained at 50Hz will fail at 200Hz. SOMA's doesn't. This matters for deployment because different robots, different actuators, different real-time OS configurations all want different control frequencies.

Certifiable safety. A Control Barrier Function (CBF) sits between the neural controller and the motors. It enforces hard constraints — joint limits, velocity bounds, torque rate limits, orientation bounds — analytically, in closed form, every cycle. The CBF doesn't "try" to be safe. It makes constraint violation mathematically impossible. This is the only path to ISO 13849 and EU AI Act compliance for neural robot controllers. We've demonstrated 84kHz throughput with zero reward degradation on the safety filter — faster than the control loop, so it adds zero latency.

Under the Hood

For the technically curious

The CfC architecture uses a backbone network to compute two candidate hidden states and a time-dependent interpolation gate:

xh = concat(observation, h_prev)
backbone = tanh(Dense(256)(xh))
ff₁ = tanh(Dense(128)(backbone))   ← candidate 1
ff₂ = tanh(Dense(128)(backbone))   ← candidate 2
τ_a = Dense(128)(backbone)         ← learned time constant
τ_b = Dense(128)(backbone)         ← learned phase offset
σ = sigmoid(τ_a · dt + τ_b)       ← continuous-time gate
h_new = (1 − σ) · ff₁ + σ · ff₂
action = Dense(12)(h_new)

The gating mechanism σ = sigmoid(τ_a · dt + τ_b) is what gives CfC its defining properties. τ_a acts as an inverse time constant — it controls how quickly each hidden dimension evolves. τ_b acts as a phase offset. Together they make the hidden state dynamics a function of real time, not discrete steps. This is why the same weights work at any control frequency.

Training uses Brax's native PPO implementation with asymmetric actor-critic: the policy observes noisy state (48 dimensions — what real sensors would provide), while the value function observes privileged state (123 dimensions — including terrain maps, contact forces, and other information unavailable at deployment). This asymmetry dramatically improves sample efficiency without compromising the deployment policy.

The entire v14 training curriculum runs sequentially across 5 simulation environments with weight continuation between phases: flat locomotion (200M steps) → rough terrain (200M) → fall recovery (50M) → handstand (100M) → footstand (100M) → consolidation (100M). Total: 850M steps, 91 minutes on one A100.
