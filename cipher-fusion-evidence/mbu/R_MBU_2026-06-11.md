# MBU — is reduced weight-bytes-streamed a real decode lever, and is it a CIPHER moat? (2026-06-11)

## PHASE 3 (2026-06-11, added) — REPRODUCIBILITY + FP8 = the cleanest 2× on the bandwidth axis
**Reproducibility confirmed:** re-ran the key points — fp16 b1 165.7→**165.9**, gptq b1 ~222→**224.6**, and the
TPW 2× point 2.00→**1.989×**. All hold within <2 %.

**FP8 (8-bit) is the best memory-bound decode lever — and gives an exact 2× on memory traffic:**

| metric | fp16 | **FP8** | 4-bit (gptq) |
|---|---|---|---|
| model bytes streamed / token | 14.48 GB | **7.24 GB (½ — exactly 2×)** | 4.05 GB |
| MBU (achieved BW ÷ peak) | 0.72 | **0.54** | 0.27 |
| decode throughput vs fp16 | 1.00× | **1.53× (b1) / 1.51–1.54× (b8–16)** | 1.35× |
| quality cost | — | ~+0.72 % PPL (prior) | larger, unmeasured |

**Two honest readings of "MBU 2×":**
1. **Memory bandwidth per token (the literal MBU axis): FP8 delivers an exact 2×** — it streams half the model
   bytes per token (14.48→7.24 GB). On the bandwidth-demand axis the lever is a clean, lossless-in-bytes 2×.
2. **Decode throughput: 1.53×, NOT 2×.** The 2× bytes-reduction converts to only 1.53× speed because the FP8
   kernel runs at **54 % MBU, not fp16's 72 %** — i.e. `lift = 2.0 × (0.54/0.72) = 1.53×`. A *throughput* 2×
   needs an FP8 kernel at fp16-level MBU (~72 %); neither vLLM's default FP8 nor forced FP8-marlin (50 % MBU)
   reaches it. So throughput-2× is blocked by the same kernel-MBU ceiling as Phase 2 — not by bytes.

**FP8 dominates 4-bit on every axis** (1.53× vs 1.35× throughput, 54 % vs 27 % MBU, half the bytes lossless-er,
lighter quality cost) and is the recommended memory lever.

### Can throughput be pushed to 2×? Kernel-level investigation (genuine attempt, honest ceiling)
2× *throughput* requires `bytes_reduction × (kernel_MBU / 0.72) = 2` ⇒ FP8 (2× bytes) at fp16-level **~74 % MBU**.
I tested whether any FP8 kernel reaches it, isolating the kernel from vLLM with a batch-1 GEMV microbench over the
real Mistral linear shapes (`fp8_gemv_microbench.py`, `fp8_gemv_triton.py`):

| kernel @ batch-1 GEMV | MBU | vs fp16 | note |
|---|---|---|---|
| **fp16 GEMV (cuBLAS)** | **0.74** | 1.00× | the bar — direct weight read, no dequant; matches vLLM 166 tok/s |
| FP8 vLLM (cutlass tuned) | 0.54 | **1.53×** | best achieved; GEMM-shaped, tile overhead at m=1 |
| FP8 `torch._scaled_mm` | 0.18 | 0.49× | GEMM kernel, catastrophic at m=1 |
| FP8 custom Triton GEMV (naive) | 0.12 | 0.33× | correct (rel-err 0.026) but unoptimized first attempt |

**Verdict: 2× throughput is physically possible but NOT achieved by any kernel in the stack — and not by a quick
custom build.** The ceiling is real: even **NVIDIA's cutlass FP8 caps at 54 % MBU** at batch-1 (1.53×), because
FP8 GEMM kernels carry tile/setup overhead that fp16's GEMV-specialized cuBLAS path avoids. A GEMV-specialized FP8
kernel at ~74 % MBU *should* exist in principle (fp16 GEMV proves the bandwidth is reachable; FP8 dequant is a
light scale-multiply), but writing one that beats cutlass is a real kernel-R&D project — my naive Triton attempt
got 12 %, worse than cutlass's 54 %. So **the honest off-the-shelf ceiling is 1.53× throughput / 2× bandwidth**;
throughput-2× is an open kernel-engineering target (uncertain), not a config away. The substrate's koopman actuator
class (it ships an fp16 GEMV decode kernel) is the natural home for such a kernel if pursued — but unbuilt/unproven.

## VERDICT: **MBU is closed for the substrate — measured, including the substrate's own kernel.** (Phase 1
established the physics and left an "untested kernel opportunity" open; **Phase 2 tested it and closed it** — the
substrate's machete kernel class sits at the same ~27 % batch-1 MBU as marlin, slightly behind it. The verdict
below is the Phase-2-final position.) Three distinct things, kept separate:
- **No utilization lever (measured, closed):** on memory-bound decode fp16 is **already bandwidth-efficient
  (MBU ≈ 70 %)** — the HBM interface is ~85 % busy delivering 2.4 TB/s. There is nothing for a substrate to "raise"
  about fp16 decode bandwidth utilization; it is near the ceiling.
- **The realized 4-bit lift is vLLM-native, not substrate (measured):** moving fewer bytes (4-bit weights) gives a
  **sub-proportional ~1.35× low-batch decode speedup** (222 vs 166 tok/s @ batch 1) via vLLM's native
  `gptq_marlin` kernel on a customer-supplied 4-bit checkpoint — the substrate did not participate
  (`anchor_loaded:false` in all 14 runs), and it carries an (unmeasured, plausibly > FP8's +0.72 %) 4-bit quality
  cost. On *this* path the substrate is not in the loop.
- **The theoretical headroom is NOT captured by any production kernel — including the substrate's own (Phase 2,
  MEASURED).** The best 4-bit kernel realizes only ~1.5× of a 3.6× byte cut because it is compute/overhead-bound
  at batch 1 (MBU ~30 %, bus ~3× idle). Phase 1 speculated a GEMV-specialized kernel could capture the ~2× gap and
  named the substrate's machete actuator as the candidate. **Phase 2 tested the actual kernels and refuted that
  optimism:** vLLM on Hopper *defaults to machete* (the substrate's kernel class) for GPTQ — so the phase-1 numbers
  were already machete — and forced head-to-head at batch 1, **machete (27 % MBU, 223 tok/s) is slightly SLOWER
  than marlin (30 %, 247 tok/s)**; awq_marlin is best at 31 % / 253; the one true GEMV-specialized kernel (plain
  `awq`) is **7× WORSE** (3.6 % MBU, 30 tok/s). All optimized production kernels cluster at **27–31 % MBU**; none
  reaches the BW-bound regime, and **the substrate's machete is not the exception — it is measured, and it loses to
  marlin.** So the ~2× headroom exists in theory (the bus is idle) but is captured by no available kernel, and the
  substrate's own kernel class does not beat the vLLM frontier.

So: **MBU is closed for the substrate, with evidence.** The *utilization* lever is closed (fp16 already ~70 %), and
the *bytes-reduction* lever (4-bit) is real but (a) sub-proportional, (b) vLLM-native, and (c) — now measured — NOT
improved by the substrate's machete kernel, which sits at the same ~27 % frontier as marlin. The only thing not
ruled out is a hypothetical *novel* kernel beating marlin+machete+awq_marlin (all ~30 %) — a hard bet against three
production kernels, with the substrate's own already in the loser's column.

## Findings (vs predictions)

1. **fp16 cudagraph decode IS weight-BW-bound — MBU ≈ 70 % (pred 1 CONFIRMED).** Step time is **flat ~6.1 ms
   from batch 1 to 16** (throughput scales linearly with batch at no per-step cost), achieved BW ≈ 2.4 TB/s,
   dmon mem 82–90 %. So fp16 decode already runs the memory interface near saturation; **"MBU" as a utilization
   number is high, and there is nothing for a substrate to "improve" about it** — the interface is the bottleneck
   and it is already busy.
2. **4-bit gives a real but SUB-PROPORTIONAL lift — 1.35×, not 3.6× (pred 2 CONFIRMED, low end).** Reducing weight
   bytes 3.6× (14.5 → 4.1 GB/step) drops step time only 6.1 → 4.5 ms. Cause (inferred from two signals, not
   isolated by a dequant-free run): the 4-bit run is **no longer BW-bound** — MBU 27 % (roofline) and dmon
   busy-time 33 %, achieved BW 0.9 TB/s, and its step time (4.5 ms) sits **3.7× above its own bandwidth ceiling**
   (4.1 GB ÷ 3.35 TB/s = 1.2 ms). High step-vs-ceiling ratio + low interface busy-time together point to the
   `gptq_marlin` kernel being **compute/launch-overhead-bound at batch 1**, not bandwidth-bound — so ~3× of the
   theoretical byte saving is left unspent. (Caveat: this diagnosis rests on the roofline + dmon signals; I did
   not isolate dequant cost with a separate kernel-level profile.) The lever is real; the *kernel*, not the bus,
   caps it — which is precisely why it is an open opportunity (Finding 4), not a hard wall.
3. **The advantage is stable across the memory-bound range, then erodes (pred 3 CONFIRMED, crossover ≈ batch 32).**
   1.34–1.37× holds batch 1–16 (both arms weight-bound, flat step time), then 1.28× @32, 1.12× @64 as decode goes
   compute-bound — 4-bit's step time grows faster (4.5 → 6.2 ms, +38 %) than fp16's (6.0 → 7.0 ms, +16 %) because
   4-bit is already compute-bound and added batch-compute hurts it sooner. So 4-bit/NF4 is a **low-to-mid-batch
   (memory-bound) lever**, fading toward parity as batch rises.
4. **MOAT — the realized lift is vLLM's; the latent lift is the open question (pred 4 PARTLY confirmed, sharpened).**
   The measured 1.35× is delivered by vLLM loading a pre-quantized GPTQ model via its native `gptq_marlin` kernel
   (`quant_method: gptq_marlin` confirmed in-JSON; `anchor_loaded:false` — CIPHER absent from every run). On this
   path the substrate is **not in the loop**. BUT "the substrate adds nothing" is **argued by absence, not
   measured** — CIPHER's own 4-bit path (machete/NF4) was never benchmarked here, so this experiment shows neither
   that it beats marlin nor that it matches it. And there is real headroom to contest: marlin realizes only
   1.35× of a 3.6× byte cut because it is compute/overhead-bound at batch 1 (27 % MBU, bus 3.7× idle). **A
   GEMV-specialized 4-bit dequant kernel driving that 4 GB read toward fp16's achieved bandwidth would reach
   ~592–825 tok/s = ~2.7–3.6× over fp16** (not 1.35×) — that is ~2× of latent speedup sitting unspent. Beating
   NVIDIA/vLLM's optimized marlin at low batch is a hard, unproven bet, but it is a **known kernel-specialization
   gap** (GEMV-tuned 4-bit kernels exist), and the substrate already ships custom-kernel actuators (machete/
   koopman) of exactly that class. So the honest moat verdict is: **the substrate has no advantage on the
   vLLM-native 4-bit path, and a head-to-head of its own 4-bit kernel vs marlin is UNRUN** — the one real
   substrate angle (a better low-batch dequant kernel) is open, quantified at ~2×, and not closed here.
   (Quality, unpriced: GPTQ 4-bit's PPL cost is unmeasured and **plausibly larger than FP8's +0.72 %** since 4-bit
   is more aggressive — the 1.35× is not free of accuracy, and the comparison to FP8's number is a floor, not an
   equivalence.)

## PHASE 2 — the decisive moat test: do any 4-bit kernel (incl. the substrate's machete) beat marlin's batch-1 MBU?
Phase 1's panel forced an honest question: I had claimed a ~2× kernel-headroom opportunity. Phase 2 tested it by
benchmarking the 4-bit kernels vLLM ships (NO custom kernel written), forcing each via `VLLM_DISABLED_KERNELS`;
kernel identity confirmed with vLLM's own `choose_mp_linear_kernel`. Decode, batch 1, cudagraph, Mistral-7B.

| 4-bit kernel @ batch 1 | tok/s | MBU | vs fp16 (166) | note |
|---|---|---|---|---|
| **machete** (substrate's class; vLLM **default** on Hopper) | 222.9 | **0.27** | 1.35× | confirmed `CHOSEN_KERNEL: MacheteLinearKernel` |
| marlin (forced) | 246.6 | 0.30 | 1.49× | confirmed `MarlinLinearKernel` |
| awq_marlin | 252.8 | 0.31 | 1.53× | best available |
| awq plain GEMV (the one "GEMV-specialized" kernel) | 29.5 | **0.036** | 0.18× | **7× WORSE** — unoptimized on Hopper |

**Findings:**
- **vLLM defaults to machete for GPTQ on Hopper** (machete is priority-first over marlin in
  `choose_mp_linear_kernel`). So **Phase 1's "gptq_marlin" was machete all along** — the substrate's kernel class
  was already in the measurement, at 27 % MBU.
- **The substrate's machete does NOT beat marlin** — forced head-to-head, machete (27 %, 223 tok/s) is *slower*
  than marlin (30 %, 247) and awq_marlin (31 %, 253). All optimized kernels cluster **27–31 % MBU**; the bus stays
  ~3× idle regardless of kernel.
- **The GEMV-specialization hypothesis is refuted by the available GEMV kernel:** plain `awq` (the batch-1-tuned
  GEMV kernel) is **7× worse**, not better — marlin/machete (GEMM kernels with batch-1-aware paths) are the
  frontier. (Caveat: vLLM's plain-awq CUDA kernel is known-unoptimized on Hopper, so this refutes "the *readily
  available* GEMV kernel wins," not "no GEMV kernel could ever win." But the substrate's actual kernel — machete —
  IS measured and loses.)
- **Proxy honesty:** I benched vLLM's machete, which is the same CUTLASS mixed-input algorithm the substrate ships
  (possibly different tuning, not byte-identical). The substrate's specific machete build is not going to beat the
  CUTLASS frontier by ~2× when vLLM's machete sits at the same 27 % as marlin.

**Phase 2 closes the moat question:** the ~2× theoretical headroom is captured by no production 4-bit kernel, and
the substrate's own kernel class (machete) is measured at the 27 % frontier — slightly behind marlin. MBU is closed
for the substrate; the only escape is a *novel* kernel beating three production kernels at once, an unproven bet.

## What this means for the 6-axis scorecard
**MBU joins MFU as effectively closed for the substrate — now with the substrate's own kernel measured.** fp16
decode is already ~70 % MBU (no utilization to raise). The 4-bit bytes-reduction path gives a real ~1.35–1.53×
low-batch lift but it is (a) sub-proportional / kernel-capped at ~30 % MBU, (b) batch-limited (fades past ~32),
(c) quality-costed, (d) vLLM-native, and (e) **NOT improved by the substrate's machete kernel, which was
benchmarked head-to-head and lost to marlin.** Recommendation: do NOT claim MBU as a substrate moat. The one
residual, unmeasured possibility — a novel kernel beating marlin+machete+awq_marlin — is a hard bet against three
production kernels all stuck at ~30 % MBU, and is not a near-term deliverable. The honest scorecard line: **MFU and
MBU are both closed substrate levers; CIPHER's deliverables remain failure-detection and TPW (+ per-GPU
reliability), not the utilization/throughput axes.**
