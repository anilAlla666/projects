# 8 Oct 2026: what was built, what was measured, what is next

Goal: a model that makes AI agents write correct graders autonomously (the Verifier Bench problem: agent-written
graders scored at chance, 0.50 to 0.52 balanced accuracy).

## 1. The judge (built first; the wrong target, kept as a component)

A 116M-parameter model trained from scratch (Kimi Delta Attention hybrid, pretrained on 2.33B tokens of permissive
Python and English) that reads an attempt plus test evidence and returns a verdict.

| Measure (dev, never trained on) | Result |
|---|---|
| Balanced accuracy, strict setting (half the existing tests visible) | 0.959 (visible tests alone 0.955) |
| Balanced accuracy, realistic setting (every existing test visible) | 0.970 (visible tests alone 0.968) |
| Faked test output or edited tests accepted | 0% |
| Correct fixes that also add a test, accepted | 100% |
| Wrong-fix verdicts flipped by a persuasive note | 2 of 623 |
| Wrong fixes that pass every visible test, caught | 35 to 48% depending on threshold |

Sonnet 5.5 as a judge on 939 real agent fixes (same inputs): 0.79 balanced accuracy, rejected 37% of correct fixes,
and accepted 4.6x more wrong fixes (6% to 27.5%) when a one-line persuasive note was added.

**Limit:** the judge reads evidence; it cannot create it. On Verifier Bench without tests it has no signal (AUC 0.53);
shown the official results it ranks attempts perfectly on 4 of 5 tasks (`docs/vb_transfer_report.md`). A judge
alone does not solve the Verifier Bench problem.

## 2. The grader writer (the right target, first attempt)

Every writer saw only the issue text and the names of the files the fix changes: no reference fix, no hidden tests.
Each written grader was self-checked on the unfixed code (a test the unfixed code passes is dropped), then run on
939 labelled real agent fixes across 80 held-out repositories (none in training).

| Writer | Usable graders | Balanced accuracy | Correct accepted | Wrong rejected | Subtle wrong rejected |
|---|---:|---:|---:|---:|---:|
| Qwen2.5-Coder-7B, untuned | 20 / 80 | 0.51 | 79% | 22% | 27% |
| Qwen2.5-Coder-7B fine-tuned on 701 maintainer test files | 34 / 80 | 0.51 | 62% | 40% | 44% |
| Sonnet 5.5 | 77 / 80 | 0.72 | 54% | 89% | 91% |

(`experiments/final/gw_scores_new_file_prompt.json`; an earlier prompt asking for edits to existing test files is in
`gw_scores_first_prompt.json`: the open models' edits did not apply because they never saw the files.)

**Findings:**
- The hard part is not catching wrong fixes: Sonnet's graders catch 89 to 91%. It is **not failing correct ones**:
  even Sonnet's graders fail about half of the correct fixes, by testing details the issue never asked for. This is
  the same failure Verifier Bench found ("invented requirements").
- The fine-tuned model produced more usable graders than the base (34 vs 20) and caught more wrong fixes, but stayed
  at chance overall. Cause: **the writer never sees the repository**, so it guesses imports, APIs and test layout;
  about 1 in 5 of its graders could not even run. Training data was also small (701 self-contained examples).

## 3. Rounds 3 and 4 (evening): repository context, then complete new test files

Same exam throughout: 80 held-out tasks, 939 labelled real agent fixes, one grader per task, no reference fix and no
hidden tests. A fix is accepted when every grader test that fails on the unfixed code passes.

| Round | Writer | Usable graders | Balanced accuracy | Correct accepted | Wrong rejected | Subtle wrong rejected |
|---|---|---:|---:|---:|---:|---:|
| 3: issue + repository context, edits allowed | Qwen 7B untuned | 18 | 0.52 | 82% | 21% | 28% |
| 3 | ours (7B, 4,000 context examples) | 20 | 0.52 | 80% | 25% | 29% |
| 3 | Sonnet 5.5 | 68 | 0.73 | 70% | 76% | 84% |
| 4: same context, asked for new self-contained test files | Qwen 7B untuned | 48 | 0.54 | 50% | 58% | 63% |
| 4 | ours (7B, 3,706 standalone-file examples) | 59 | 0.54 | 37% | 72% | 73% |
| 4 | ours after the reward-filtered round (20 examples) | 59 | 0.55 | 44% | 67% | 68% |
| 4 | Sonnet 5.5 | 75 | 0.77 | 68% | 86% | 93% |

(`experiments/final/gw_scores_round3_context.json`, `gw_scores_round4_standalone.json`.) Round 4 changed the runner
as well as the prompt: a grader's diff now gets a `diff --git` header per file, and a new file may replace an existing
one. Round 3 and round 4 numbers are therefore not directly comparable; within a round every writer had the same
prompt and the same runner.

**What round 4 established:**
- **Format is solved.** Round 3's open-model graders mostly failed to apply (725 of 1,031 runs): they edited test
  files they could not see exactly. Trained on complete new test files built from the maintainers' patches
  (`gw/standalone.py`: the patched file's imports and helpers plus only the added or changed tests), all 79 of ours
  apply. The converted examples are as valid as the originals: on 154 tasks, 73% fail on the unfixed code and pass on
  the gold fix, against 71% for the maintainers' own patches in the same runner (`gw/val_targets.py`).
- **The remaining failure is invented requirements.** Our graders now run and catch more wrong fixes (72% against
  58% untuned), but fail 63% of correct fixes. Read on 16 cases: almost every failure asserts a detail the issue never
  fixed: an exact number, an exact string, an exception type, a constructor argument or attribute name the real fix
  did not use. Sonnet does the same at about half the rate.
- **The reward-filtered round could not get traction.** Of 1,184 drafts on 296 training tasks, 657 failed on the
  unfixed code, 34 passed every known-correct fix, and 20 also caught a wrong one. Keeping only the individual tests
  that pass every correct fix raises this to 62 drafts on 38 tasks, too few to train on. 0.553 against 0.542 is noise.
- **No acceptance rule rescues it.** On the training-task runs (4 drafts per task), accepting when most tests pass
  moves balanced accuracy from 0.51 to at best 0.54 (`gw_decision_rules_dev.json`); no rule was applied to the exam.
- **Disclosure:** the round-4 model was trained on the build before two converter fixes (a stop command missed the
  first training run; the corrected run then ran out of memory beside it, and the first run saved). The runner's
  header fix makes its output apply; the missing base-class fix affects a small share of examples.

**The deciding measurement (9 Oct, 02:45 BST).** Remove from each round-4 exam grader every test that a correct fix
fails (an oracle filter, using the exam's labels, so a ceiling and not a result):

| Writer | As written: BA, correct accepted, wrong rejected | Invented tests removed (ceiling) |
|---|---|---|
| Sonnet 5.5 | 0.769, 68%, 86% | **0.854**, 100%, 71% |
| ours (7B) | 0.542, 37%, 72% | 0.561, 100%, 12% |

Sonnet's graders carry real signal under the invented tests: a perfect filter lifts them to 0.85. Ours do not: almost
everything they caught was caught by the invented tests, which fail every fix. So the 7B is not worth more work as a
writer, and the model worth building is the filter: given the issue and one written test, predict whether it asserts
something the issue does not require. Its labels come from execution (a test that a correct fix fails is invented),
it needs no reference solution at use time, and it works on any agent's graders.

## Why the 7B did not move (diagnosis, 9 Oct, 03:00 to 03:30 BST)

Every kept test on the round-4 exam, classified by what it does on the labelled fixes (`gw/crash_rule.py`,
`experiments/final/gw_scores_round4_qwen32b_untuned.json`):

| Writer | Kept tests | Fail every fix (broken) | Pass every correct fix and catch a wrong one | Tasks with at least one such test | BA |
|---|---:|---:|---:|---:|---:|
| Qwen 7B untuned | 102 | 72% | 20% | 14 of 50 | 0.54 |
| ours (7B, standalone SFT) | 164 | **90%** | 9% | 13 of 62 | 0.54 |
| Qwen 32B untuned | 170 | 58% | 31% | 27 of 62 | 0.57 |
| Sonnet 5.5 | 309 | 11% | 70% | 66 of 75 | 0.77 |

1. **Our tests are broken, not subtly wrong.** 90% fail on every fix, correct and wrong. Run on one correct fix per
   task, about half call the code wrongly (unexpected keyword arguments, attributes and names that do not exist) and
   about half expect values the code never produces.
2. **The self-check hid it.** "Keep tests that fail on the unfixed code" keeps a broken test, because it fails there
   too; the 72% "wrong rejected" was those tests rejecting everything. The reward round then had almost nothing to
   learn from (3% of drafts good).
3. **Fine-tuning made it worse (72% to 90% broken).** In 57% of the training examples the maintainers' tests use
   names that appear nowhere in the prompt (23% of all names they use): they were written by someone who knew the
   fix. Imitating them teaches a small model to make up API and values. Sonnet also uses unseen names (78% of its
   graders) but mostly correctly, from knowledge of these libraries.
4. **Not the prompt.** With a test file the maintainers changed shown, ours is 89% broken; with none, 87%.
5. **Size helps and does not close it.** The untuned 32B doubles the tasks with a working test (27 against 13) and
   stays far below Sonnet (66).
6. **No cheap tell on the unfixed code.** Only 11 of our 147 broken tests crash there with an API or name error;
   the rest fail an assertion, as good tests do.
7. **One reference-free rule works when many attempts are graded together** (as on Verifier Bench): drop any test
   that fails on every attempt. It uses no labels. Sonnet 0.769 to 0.804, 32B 0.566 to 0.613, ours 0.542 to 0.555
   (nothing real is left under its broken tests).

## 4. What would move it (next session)

1. **Let the writer execute code before it asserts.** The wrong values are guesses about behaviour the model could
   observe: run the unfixed code on the issue's example, read the actual output, and assert only the part the issue
   says must change. This is the difference between Sonnet's graders and ours, and a 7B cannot close it by imitation.
2. **A larger open base** (Qwen2.5-Coder-32B with the same standalone data) to test whether the guessing is a
   capacity limit.
3. **Then the reward-filtered round again**, which needs a writer whose drafts pass correct fixes often enough
   (3% today) to give hundreds of training examples, and more training tasks with labelled fixes (300 used).

## 5. What would move it (written at 16:30, kept for the record)

1. Give the writer the repository context it needs: the source of the files the fix touches and the existing test
   file it should extend. Rebuild the 16,000-example training set in that form (files read from the SWE-rebench
   images), so the writer learns to write tests that run and that check only what the issue requires.
2. Penalise rejecting correct fixes explicitly: score candidate graders on known-correct and known-wrong attempts
   (we have both for every training task) and train toward graders that pass the correct ones, by rejection sampling
   or reinforcement learning with that reward.
3. Then test on the Verifier Bench Terminal-Bench tasks, which need the same writer applied to a different output
   format (a test script that writes 0 or 1).
